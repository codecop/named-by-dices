# Commit

## Commit rules for this project

Format:

```
git commit -m <Commit message here>

Generated by Mistral Vibe.
Co-Authored-By: Mistral Vibe <vibe@mistral.ai>
```

Rules:

- Always use `git commit` - never any other way to commit changes
- Footer mandatory: every commit ends with `Generated by Mistral Vibe.` and the `Co-Authored-By` line
- Commit often after each increment - small, frequent commits instead of big batched commits
- Push every commit immediately - locally with `git push origin <branch>`; in the cloud sandbox with `scripts/api_push.py` (see below)
- Cloud sandbox only: on first use of `scripts/api_push.py`, pass a personal access token **in the chat**; it is stored in `~/.push-token`, which is **created with chmod 600 if missing** and never committed or printed. The gh executable's own token is not used (read-only in the sandbox).
- NEVER change history in version control. This includes:
  - Never do `git reset --hard`
  - Never do `git rebase`
  - Never do `hg strip`
  - Never do `hg rebase`

Example:

```
git commit -m "Add user authentication feature

Generated by Mistral Vibe.
Co-Authored-By: Mistral Vibe <vibe@mistral.ai>"
```

## Push

- **Locally (Windows etc.):** plain `git push origin <branch>` works - no token handling needed.
- **Cloud sandbox only:** `git push` is rejected by the sandbox proxy with 403, so use `scripts/api_push.py` instead. The GitHub REST API (api.github.com) is allowed there and the token has Contents: write permission. Therefore:

1. Work locally with `git commit` as usual (rules above).
2. Push with `python3 scripts/api_push.py [--branch main]` - the script needs a personal access token with repo write access, passed in the chat on first use and stored in `~/.push-token` (created with chmod 600 if missing; `API_PUSH_TOKEN` is honoured too). In the sandbox, `git push` is blocked (403) and gh's mutating API calls are blocked as well, so the script talks to api.github.com directly via raw HTTPS and replays the local commits via the git data API (blobs -> tree -> commit -> PATCH ref). The repo is derived from `git remote get-url origin`.
3. In a new cloud session: clone the repo with `gh repo clone <owner>/<repo>`, pass the token in the chat once, then run `scripts/api_push.py`.

The token is never written into the repo or printed.

## Notes (cloud machines only)

1. Do not waste time on `git push` variants: a fresh `gh repo clone` does not help; `git push` with `GH_TOKEN` or with a PAT supplied via `-c credential.helper=...` is rejected by the sandbox proxy with 403 (receive-pack is blocked regardless of the credential); raw `Authorization: token/Bearer` against the git smart-HTTP endpoints via python returns 401. In the sandbox, only the REST API via raw urllib with a PAT can write.
2. `scripts/api_push.py` creates new commit SHAs server-side, so `git status` shows "ahead/behind" even when the content is identical. Check sync by **tree SHA** only (`git rev-parse HEAD^{tree}` vs. `GET /repos/<repo>/git/commits/<main-sha>` -> `.tree.sha`), never by commit SHA. The script itself finds the base commit by comparing trees for the same reason.
3. Pulling upstream after API pushes: `git pull` would report conflicts everywhere because local and remote commit SHAs diverged (merge-base is the original commit); `git merge origin/main` resolves cleanly because the replayed commits have identical trees. Never use `git reset --hard`/`git rebase` to "fix" the divergence (see rules above).
